# Engaging an existing project

An existing project already made most of the decisions that matter: where meshes come from, how they are named,
what the importer does with them, what a budget is. Authoring against those decisions is cheap; discovering them
by failing an import is not. This protocol is *(inference)*, assembled from the failure cases in the
[evidence](evidence.md): renamed meshes breaking collision, exporter defaults changing output, unit and axis
mismatches, validators passing while engines drop geometry.

## 1. Read before choosing

- The project's agent instructions, README, docs and any asset-pipeline notes. They override this skill.
- The asset folders: source formats (`.blend`, scripts, CAD), exported formats (GLB, FBX), who produced them.
- Existing generator code. If scenery is generated by code today, a new hand-made asset is a different pipeline,
  not an extension of it.
- The verification the project already runs (tests, receipts, screenshots). New assets must pass the same gate.

## 2. Fill in the contract card

Write the answers into your notes (or the project's docs if it has a place). Mark each **known** (read it),
**inferred** (guessed from files) or **unknown** (ask or test).

| Item | Answer | Basis |
|---|---|---|
| Source of truth for this asset class (script, `.blend`, CAD, code) | | |
| Engine and version; importer (Interchange, legacy FBX, glTFast, ...) | | |
| Up axis, forward axis, units, pivot convention | | |
| Naming rules, including collision prefixes and LOD suffixes | | |
| Materials: slot count, names, vertex-color use, texture policy | | |
| Collision: simple/complex, who authors it, `CollisionTraceFlag` | | |
| LOD and Nanite policy; triangle and draw-call budgets | | |
| Instancing expectations (one mesh many copies vs unique) | | |
| Rig, animation and morph conventions (if any) | | |
| How an asset is imported (command, editor steps, pipeline options) | | |
| How it is verified (tests, receipts, screenshots, who looks) | | |
| Where sources live and how an output is rebuilt | | |

## 3. Choose the least surprising route

- If the project already imports a format from a tool, extend that tool and format.
- A new dependency (Blender, Unreal editor automation, a CAD kernel) or a Beta engine feature is a decision for the
  owner. Put the options in front of them with time, risk, complexity, best-practice distance and maintainability.
- When two routes are close, prefer the one the agent can verify without a person.

## 4. Prove with one asset

1. Author one small representative asset by the chosen route.
2. Run it through the project's real import and its real verification.
3. Look at the result inside the engine (not only a viewer): scale, orientation, collision, materials, LOD.
4. Fix the *route* if anything differs from the card, then update the card.
5. Only then author the batch.

## 5. Leave the project better documented

- Commit the source script or file, its parameters and the one command that rebuilds and verifies the asset.
- Record the filled-in contract card where the project keeps pipeline notes.
- State what you verified and what you did not ("imports into UE 5.8 via Interchange with names intact"; not
  "works in Unreal").

## Stop and ask when

- The contract card has an unknown that changes the route (importer, collision convention, Nanite policy).
- The project has no verification at all for this asset class.
- The chosen route needs a tool the machine does not have; say it is missing rather than substituting.
